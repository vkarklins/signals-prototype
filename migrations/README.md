# Database migrations

Fresh databases use the full `schema.sql`, automatically loaded by Docker on the
first startup of an empty database volume. Existing volumes are not reinitialized.
Do not delete a volume to apply a schema change.

## 001: Configurable Signal detection

This adds `signals`, `signal_versions`, `signal_runs`, and `signal_events`, plus
constraints and indexes. It leaves `turns`, `results`, and their data unchanged.
It does not seed detectors, call models, or enable analysis.

From the repository root, with the existing database container running:

```bash
docker compose exec -T db psql -U signals -d signals_prototype -v ON_ERROR_STOP=1 < migrations/001_signal_detection.sql
```

Apply this migration **once**. It uses an explicit transaction: if any statement
fails, no migration changes are committed. A second application fails rather
than silently accepting an existing but potentially incompatible schema.
`ON_ERROR_STOP` makes the command report failure. No migration runner or tracking
table is installed; record successful application in your deployment notes.

To inspect the result:

```bash
docker compose exec db psql -U signals -d signals_prototype -c '\dt'
```

## Data contract

- UUID primary keys are generated by the future application, not by a database extension.
- Signal names are case-sensitive and unique. Required text must contain more than spaces.
- New signals default to disabled. The highest version is the active configuration;
  immutable versions are an application convention, not enforced by a trigger.
- Each turn/Signal/version has at most one logical run. Manual retries reuse it,
  resetting `finished_at` and `error` when returning to pending/running.
- Terminal runs require `finished_at`; pending/running runs must not have it.
  Successful runs require an object `input_snapshot` and no error.
- `supporting_span_ids` is nullable for summarizer compatibility. If supplied,
  it must be a nonempty UUID array without null elements.
- `output_schema`, `payload`, and populated `input_snapshot` must be JSON objects.
  The future application must validate JSON Schema, payload conformance, and
  cited span membership; the database only checks JSON object shape.
- Foreign keys restrict deletion of referenced rows. The application must save
  findings and successful run completion atomically. These tables contain no
  probability column; frustration scores remain in `results`.

## Verification

Use a disposable database through `TEST_DATABASE_URL`, never the application's
`DATABASE_URL`. Tests create and remove isolated schemas in that database.

```bash
python -m unittest discover -s tests -v
```

The schema checks compare fresh and migrated database definitions, verify existing
data preservation and transaction rollback, and exercise constraints and nullable
span references. They skip when `TEST_DATABASE_URL` is unset.

## 002: Run human labels

Apply once after migration 001 to add shared editable labels for Signal runs:

```bash
docker compose exec -T db psql -U signals -d signals_prototype -v ON_ERROR_STOP=1 < migrations/002_signal_run_reviews.sql
```

Restart/rebuild the API afterward. Existing runs remain unreviewed and original
findings are preserved. Fresh databases include this table in `schema.sql`.
